## Boundary and implementation assessment

- The account API obtains the account ID from Clerk server auth. The profile handler rejects unknown fields and cross-origin mutations, bounds payload size, validates domain/use-case IDs, writes only the `privateMetadata.datummOnboarding` namespace and returns private no-store responses. Existing permission metadata is not accepted from request bodies. Live Clerk reads, deep-merge behavior and persistence were not exercised by this reviewer; dependency-injected tests alone do not establish the deployed account contract.
- Output registration uses stable primitive dependencies rather than the changing context object, avoiding the obvious registration/re-render loop. The provider is keyed to the task ID, so outputs do not intentionally carry across selected tasks. Drawing content remains mounted while an answer output is visible, and Focus drawing changes layout rather than creating another editable canvas instance. State/camera restoration still needs browser interaction evidence.
- Answer projections are explicitly read-only, retain task/answer identity and distinguish streaming, partial and saved text. CSV export escapes quotes and prefixes formula-like cells. Renderer defaults disable raw HTML and configure strict Mermaid. This review found no new native approval action attached to Markdown, output navigation, CSV or drawing context.
- Existing native actions continue to use exact proposal, approval hash, document identity, expected revision and task version. Source preservation is not proof of live Revit authorization or execution correctness.
- D9 authoritative schedule/BOQ revision storage, current-revision history and model provenance are not implemented by the answer-output projection. It correctly avoids claiming those semantics; this remains a capability dependency, not a verified completed backend feature.
