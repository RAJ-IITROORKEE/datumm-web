# Integration contracts for the renewed workspace

12 November 2026. Planning specification; application implementation is not authorized by this document. Read [PROJECT.md](../../PROJECT.md), [PLAN.md](../../PLAN.md), [PRODUCT.md](../../PRODUCT.md) and [structured outputs](structured-output.md) first.

DATUMM is a Cursor for Revit. This contract keeps conversational reasoning, agent-updated review outputs and native model authority distinct. D6–D7 approve reports, CSV tables/schedules/BOQs and Mermaid with larger previews beside chat; schedules are review sheets without formulas or direct cell editing. D9 approves automatically making a successful non-native agent revision current, showing its change summary and keeping previous revisions accessible. Native changes retain exact approval. D10 starts with individual accounts; teams remain later scope.

## Provisional output record

The following is a **provisional semantic contract**, not an existing wire schema, endpoint promise or instruction to replace upstream report JSON. First obtain sanitized deployed fixtures and map them; add fields/adapters only where a gap is confirmed.

| Field group | Required meaning |
| --- | --- |
| Identity | Stable `artifactId`; immutable `revisionId` and revision sequence; `schemaVersion`; `kind` (`report`, `schedule`, `boq`, `mermaid`); title; creation time; owning individual account/project/task and source turn/command. Server supplies authoritative ownership. |
| Lifecycle | `draft`, `ready`, `failed` or `cancelled`; current ready revision reference; prior revision reference; generating command identity; structured change summary. Partial content must not masquerade as an exportable completed dataset. |
| Provenance | Origin (`design_derivation`, `revit_extraction`, `estimate`, `user_supplied`); exact document ID and model revision when native; exact plan ID/version/fingerprint when derived; source/evidence references; observation time; coverage/scope and limitations. Unknown fields remain unknown. Mixed origins require row-level provenance. |
| Report | Saved Markdown plus references to associated typed tables/diagrams; explicit assumptions and unresolved findings. A fluent answer is not proof of model verification. |
| Schedule/BOQ | Typed column definitions (stable key, label, value type, unit); stable row IDs; raw typed values; optional actual source element/room IDs; explicit missing values, scope, paging/count/coverage. Do not use row position or room label as native element identity. |
| Diagram | Mermaid source, format/version metadata, textual description and evidence links where applicable. Rendering cache may be derived; source remains reviewable after rendering fails. |
| Export | Formats authorized for this exact ready revision; revision-bound retrieval/export reference; MIME type, filename and source/coverage metadata. No arbitrary model-authored URL becomes a privileged download. |
| Integrity | Optional content hash with specified canonicalization. Reuse a backend hash only if its meaning is documented; a report hash must never be treated as a native proposal approval hash. |

BOQ baseline columns: category/element or item, description, quantity, unit and source reference where known. Counts, lengths, areas and volumes remain dimensionally distinct. Rates, currency and amounts appear only if real data is provided and scope is agreed. No formulas, in-browser cell changes, inferred rates, or fabricated native IDs.

### Read, update and export semantics

1. Open an artifact at an explicit revision; show origin, source version, completeness and stale-source status. The current pointer is a convenience, not permission to mix source versions. A user viewing history sees a clear historical label and can return to current.
2. A revision request goes through the shared composer. A future structured context reference must carry artifact/revision, selected row IDs if any, source binding and the user's prompt. Current free-text follow-up alone does not establish authoritative row selection. Selected rows are context, not direct cell editing.
3. The service validates account ownership and expected task, artifact and source versions, uses an idempotent command and generates an independent revision. Old ready data stays available while the next revision is streaming or fails.
4. On successful complete validation, the service atomically commits the new immutable revision, moves the current pointer and records a change summary. **D9: it becomes current automatically; no “Use this revision” approval is required.** If the user is reading an older revision, preserve that view with a new-current notice. Do not silently rewrite a historical page under review.
5. A concurrent change must produce a documented conflict/rebase result; never silently overwrite newer data or retarget the user's selected rows. Failed/cancelled/stale work stays distinguishable and does not displace the last ready revision. Exact state names/status codes remain provisional.
6. Export resolves the explicit revision at click time and returns the same source binding, columns and full authorized dataset. Changing current during download must not change that download's dataset. Filtering/sorting affects export only when the scope is explicit (entire revision vs selected rows).
7. Streaming Markdown and table copy are presentation conveniences. Full-schedule exports come from typed rows, not a scrape of a truncated rendered table. Escape quotes, delimiters, embedded newlines and Unicode correctly; neutralize spreadsheet formula injection in untrusted textual values while preserving legitimate numeric quantities. Document the chosen CSV dialect, encoding and numeric/null rules.

Do not assume the backend has artifact listing, revision fetch, update, diff, paging or revision-bound export APIs. No such generic route is established by S4–S6. Proposed paths must wait for actual service contract review; adding a frontend link without a server route is insufficient.

## Event and compact activity contract

Preserve the current task projection's cursor, monotonic task version, duplicate suppression, cross-task rejection and gap buffering (S3). The current transport forwards events from SSE and concatenates `answer` detail; verify whether deployed `answer` events are deltas or full text before changing rendering. Task snapshots remain the recovery authority after a disconnect. Browser stream end is not proof of task completion or cancellation.

The provisional extension needs stable task/turn/step/agent/tool-call identities, event identity and sequence, lifecycle status, timestamp, parent relationship, and references to artifacts/revisions. Prefer existing fields (`agent.id`, `parentStepId`, tool `callId`, session IDs) where the service actually supplies them. Define correlation for concurrent calls to the same tool: the current compact row matcher closes an open call by name (S8), which is insufficient to disambiguate identical parallel calls. Do not claim richer correlation before the backend supplies it.

The summary says what actually ran and whether it is running, waiting for input, blocked, partial, failed, cancelled, interrupted or complete. Existing `TurnProcess` maps many statuses to running/done/failed; audit these mappings when integrating the richer state matrix. A blocked job is not an actively executing worker. Missing child metadata yields the supported flat fallback; an empty manifest must not become a decorative team roster. Distinguish plan checklist items from recorded executed steps. Keep raw tool input/output and session IDs expandable, with safe redaction where required.

Artifact activity is provisional: producing, revision ready, revision failed and source stale may be projected from snapshots or events once the service agrees a schema. Reconnect must reconcile the same revision/command, not launch a second revision. Advisory specialists (`nativeAuthority: 'none'`) may recommend changes but cannot approve or execute Revit modifications.

## Exact Revit approval and verification

Preserve the two existing integration paths rather than collapsing them into a generic “Apply” action:

- **Hosted task path:** `approve_exact_proposal` / `refresh_exact_proposal` carry proposal ID, approval hash, document ID and reviewed revision inside the existing versioned/idempotent task command envelope (S9). Plan acceptance, Build mode and placement preparation are distinct preceding actions.
- **Desktop native-build path:** `nativeBuildAction` carries expected task version and exact proposal identity with expected document revision; the conversation checks desktop availability. Refresh re-reads the saved proposal and validates that document/design/proposal identity still matches (S9). A connected web tab must not imply that this bridge exists.

Review must show the actual target model/document, level/view where relevant, units, coordinate frame, exact operations/targets, type/host choices, deletion closure, reviewed revision and expiry. Native execution must reject changed/expired/mismatched authority on the server/connector, even if a stale browser button remains visible. A refreshed proposal requires review of its new identity. No report/schedule update, Mermaid interaction, annotation, selected row, “current revision” change, plan acceptance, model selection or Ask/Plan/Build switch grants native permission.

Keep preview, dispatch, commit and independent read-back verification separate. A committed operation with incomplete verification is not “verified”; unknown outcome requires inspecting the original operation ID before any new write. Reconcile/retry must retain that identity so reconnects cannot duplicate elements. A partial native build does not imply the user's overall design goal is complete. No save/sync is promised by the current approval UI (S9).

**Existing authority decision still open:** legacy concept Full Access describes one automatic exact-proposal approval, 30-minute expiry and a 120-element cap, with revocation; task Full Access has another review flow (S10). These are source-visible controls, not approval for a new autonomy policy. Confirm actual server enforcement and choose retain/restrict/defer explicitly with the user. Do not silently broaden these controls or present a non-native D9 update as permission to use them. Until resolved, new output interactions always route native writes through a separately reviewed exact proposal.
