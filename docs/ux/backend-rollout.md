## Candidate, deployment and rollback checklist

These are later steps for an explicitly authorized release, not actions performed here.

1. **Review and isolate.** Inventory the exact candidate against the then-running source/image, include the two new modules and five checks, exclude unrelated native/local changes, review all interdependent hunks and line endings, and record a reproducible immutable source identity. Keep merge, push and release as separate decisions. Establish the graph freshness disposition without overwriting saved semantic nodes.
2. **Qualify the actual artifact.** Use the legacy `apps/domain-api/Dockerfile` and its allowlisted `Dockerfile.dockerignore`, building from the reviewed repository root with a source identity matching the candidate. The Dockerfile's documented local build is `docker build --file apps/domain-api/Dockerfile --tag datumm-orchestrator .`; pass the verified candidate's full `SOURCE_COMMIT` build argument and qualify the target Linux architecture. Run the five controlled checks and relevant full backend/integration checks against that exact source; build and exercise the actual Linux image, including imports, planner and isolated storage/auth/streaming checks. Record the image digest and provenance. Do not substitute `.github/workflows/hosted-container-check.yml` or `apps/domain-api/hosted/Dockerfile`: those target the isolated OpenCode canary, not the legacy service.
3. **Revalidate infrastructure read-only.** Verify the current running digest, source commit, ECS/CloudFormation template and parameters, task execution role, health, authorized origins, backup and restore procedure, worker state, and service/volume ownership. The prior owner-approved [repo image deployment record](../../../_wt-orch-build/docs/verification/aws-repo-image-deploy-2026-11-12.md) describes the historical `datumm-orchestrator` stack in `ap-south-1`, an on-demand Mongo dump, an immutable ECR digest, change-set review and singleton ECS replacement with potential downtime. Its final recorded follow-up used image digest `sha256:40849e235a0cba9a2a9521d975aa1b65ec1d0a2f411cc32cb0c4595773d2f7ef` from source `2aace05…`; the record says the change set updated `ImageUri` and affected the ECS task and service. It is historical, not a current executable recipe or evidence that the same digest is still live. Do not expose credentials or secret values.
4. **Plan cutover.** Agree a quiet window and backup verification, retain the exact previous image digest and compatible repository permission, and prepare a change set whose intended changes are limited to the reviewed image/task and necessary execution-role repository access. Reject unexpected host, volume, database, origin, or distribution changes. Confirm the backup can be restored separately; do not assume a container rollback reverses persisted task state.
5. **Post-release checks.** Verify health/source identity, ECS steady state and logs, signed-in history and a read-only Ask/follow-up including streaming and usage ownership. On a disposable read-only task, qualify pause, reload, Continue, cancel to authoritative terminal state, and reload; never use a native write to exercise cancellation. Check new question provenance and presentation behavior where a controlled non-native task can establish it. Actual provider output may omit optional presentation. Preserve explicit proposal approval and distinguish unknown native outcomes from verified reconciliation.
6. **Rollback decision.** If candidate health or agreed checks fail, restore the exact pre-release image digest and repository permissions recorded in step 3 using a separately reviewed change set; verify health, owner-scoped history and recovery. A prior historical rollback target is not assumed to be today's correct image. Database restoration is a separate consequential decision only if data damage is established; inspect compatibility of newly persisted fields, cancellation flags and statuses first. Never replay an uncertain native operation or infer rollback from a service restart.

Open release dependencies include live shared-ledger qualification, hosted cancellation after deployment, research-source quality, native OpenCode hosting/integration, immutable BOQ history, billing contracts, and separately authorized Revit approval/read-back. No claim in this packet closes those gates.
