# Architectural agent and retrieval MVP

**21 November 2026 · proposal for review.** An architect should be able to ask for a concept, see what DATUMM understood, watch the work advance, inspect the evidence, and reopen the result tomorrow. The first release should prove that journey with one reliable workflow. Additional Revit and design tools can then join the same harness independently.

## The first production scenario

Start with the supplied example, “hi plan a 3bhk layout for revit floor plan of 20x30m.” The screenshot shows **Ask**, a **Completed** heading, **Checklist · 0 of 2**, and a link to read the answer. It supplies neither the saved answer nor the two step records. The screenshot therefore establishes a presentation failure and leaves the run outcome open.

In Ask, acknowledge the three-bedroom brief and the 20 × 30 m dimensions inline. Distinguish plot size from buildable footprint, and offer **Continue in Plan** with that brief intact. In Plan, group the questions that materially affect the drawing. Offer provisional assumptions where appropriate. Advance through the available read, generate and check steps automatically. Show the resulting concept revision and room schedule together. A requested Revit build starts with a connected document, an exact change preview and the architect’s approval. Completion of a design concept and completion of a Revit write have different evidence.

## Architecture and ownership

Persist one idempotent receipt per accepted command. Correlate the task, turn and execution attempt across pauses, retries and mode changes. The browser sends commands and projects events. The existing AWS orchestrator owns the plan, budgets, step transitions, tool policy and terminal assessment. Start with modules inside the existing service. Introduce an independent worker only where ingestion or rendering needs isolation, independent scaling or durable background retries.

| Module | Responsibility and boundary |
| --- | --- |
| Agent harness | Interpret the brief, choose the next allowed step, persist its result, test completion predicates and continue. Each attempt has a deadline and budget. Repeated calls with the same normalized inputs and evidence trigger one alternate strategy or a partial outcome explaining the blocker. A disconnected browser can reattach. A worker restart reconciles uncertain effects before retry. |
| Catalog, skills and MCP | One typed catalog shared by built-in and external tools. Each entry declares input/output schema, modes, scope, read/write effect, approval and timeout. The dispatcher enforces these in code. Versioned skills guide tool use and declare prerequisites. Candidate architectural skills include brief intake, sheet comparison, schedule preparation and concept review. Tool permissions come from the catalog at execution time. |
| Documents and design | Separate providers for document reading/rendering and architectural geometry/checks. Generate artifacts from the saved plan/report revision, validate files, persist hash and provenance, then issue an owner-scoped file ID. Begin with an existing export or printable review and add editable DOCX/XLSX once the readback works. Design results identify assumptions, units and revision. |
| Revit | Connector adapter exposes capabilities per active document. Reads return document identity and revision. Writes require a preview, explicit approval bound to that revision, idempotent dispatch and read-after-write verification. Lost connection or a changed document pauses the step. A generated concept can finish while a requested native operation remains pending. |
| Retrieval and web | Source ingestion, scoped retrieval, public search and evidence opening are independently callable tools. A common evidence reference carries source type, owner/project scope, version/content hash and an address within the source. Public web evidence includes URL, retrieval date and supporting passage. Preserve N4’s existing report-reference format for saved conversations. |
| Model and speech adapters | The model registry supplies capabilities and limits for reasoning, vision, speech and optional routing. The harness decides what inputs a given call may receive. Capture provider latency, usage and cancellation per operation. |

## Architectural RAG and research

1. **Ingest and version.** Start with project specifications, text/scanned PDFs, exported floor-plan sheets and PNG/JPEG design images. Hash original bytes. Persist project ACL, source version, parser version, page size/rotation, extraction status and thumbnails. Keep text spans, table headers, OCR polygons, sheet number and view/level where available. Mark a replacement as a new revision. Route native RVT through an authorized connector export. Show unsupported CAD formats with an actionable conversion path.
2. **Retrieve and inspect.** Apply tenant/project/revision filters before candidate retrieval and again when opening a source. Use lexical matching for sheet numbers, dimensions and material codes, semantic retrieval for descriptions, and page tiles or visual representations for image questions. Fuse and rerank candidates. Benchmark the added visual channel against text/OCR alone. Preserve coordinates through rotation and zoom. A visual resemblance supports a design observation. Dimensions need legible annotations or calibrated geometry with units. [Example page geometry contract](https://docs.aws.amazon.com/textract/latest/dg/text-location.html)
3. **Run a bounded research loop.** Plan the question, retrieve candidates, open the best pages or regions, check support and contradictions, then answer with citations. Allow a bounded reformulation when evidence is insufficient. Search public sources when the question calls for external information. Send a minimal public query, keep private project content scoped, and record jurisdiction, edition and publication date for standards. Missing or conflicting evidence produces a qualified answer or a focused question.
4. **Prove the citation.** A saved citation opens the same source version, page and highlighted region after reload. Revocation or deletion invalidates future access, including cached results and thumbnails. A superseded version remains explicitly historical when the user has access. Treat extracted text as source material. Instructions within a drawing, PDF or web page have no tool authority.

## Production acceptance and operating limits

Proposed pilot gates, to calibrate with architects before release. Build a held-out set of at least 30 tasks across briefs, schedules, noisy/rotated sheets, visual references, ambiguous units, conflicting sources and absent evidence. Add separate negative fixtures for cross-project filenames, revoked access, stale approvals and duplicate commands. Publish raw counts with rates.

- **Answer and task quality.** The three-bedroom walkthrough passes in Ask and Plan. Every required step under a “completed” goal has a verified outcome. Check terminal, partial and blocked views after refresh. Two reviewers inspect whether the plan and outputs satisfy the brief.
- **Evidence.** Proposed initial gates are at least 90% correct page/sheet retrieval in the top five on answerable labeled cases, correct version and locator on every published golden citation, and zero cross-project disclosures or unauthorized native actions. Score unsupported answers and correct abstentions separately. Record missed sheets and wrong-region matches.
- **Performance and cost.** Baseline p50/p95 for acknowledgement, first useful text, first cited result, full completion, tool duration, model calls, search/OCR cost and upload-to-ready time on the same inputs. Agree numeric latency and per-run spend limits from the pilot before broad rollout. Show a recoverable status on provider timeout or budget exhaustion.
- **Operations.** Test slow/restarted workers, duplicate requests, disconnect during a tool call, source removal, renderer failure and a disabled MCP server. Confirm redacted traces can explain the stop reason and identify version/receipt without logging private plan content. Exercise restore of source metadata, retention/deletion, and provider shutdown while previously saved outputs remain readable to authorized users.

### Phase 1 local result

Approved and implemented on 21 November 2026. The chat uses the existing Markdown renderer for short and structured answers. Long excerpts can expand in place using a keyboard-accessible disclosure. The full-answer and table controls still open beside chat.

The checklist uses recorded turn evidence. A saved partial response shows **Partially complete**. A finished response with unchecked steps shows how many are confirmed and exposes the unconfirmed steps. A recorded failure, cancellation or block takes precedence. Historic responses with no turn-bound evidence cannot establish a checklist.

The Codex in-app browser exercised the exact 3BHK prompt through the local AG-UI fixture. Ask saved and reloaded one inline answer with two unconfirmed steps. Pressing Enter opened the checklist and showed both. Plan recovered from a stream interrupted after persistence and restored the table of room areas and 2 of 2 checklist on reload. The historical fixture retained its inline answer. The 390-pixel viewport showed no horizontal page overflow. The fixture synthesizes the task and stores its projection in the browser session for local replay.

The web tests, typecheck, `lat check` and the local production build passed. The build needed one worker on this machine after the default workers exhausted available memory. All 19 production smoke checks passed, and the new fixture returned 404 in production mode.
