## Behavior contract

Running: one quiet Working/current-public-step row, a recorded checklist when available, and an expandable process disclosure. Keep tool internals and detailed evidence in Activity. Announce meaningful status changes without narrating every streamed token; respect reduced motion and reading position. Do not expose or manufacture private chain-of-thought, intermediate model bookkeeping, elapsed times or parallel agents.

Completion:2–3 short sentences explaining the actual result, material limitation and next useful action. Keep approval requirements, partial results and uncertainty visible. Do not use CSS line clamping or arbitrary text truncation as a purported summary. Drawings and full report/schedule contents open in the existing right work area through exact identity-bound links. Preserve full saved answer content independently of the compact presentation. Copy must make clear whether it copies the summary or full answer.

Illustrative concept result: “Prepared three concept options for the12×9m footprint. Review them in Design; Revit has not been changed. Choose an option or request an adjustment.” Counts, dimensions and native-write status must come from the actual task, not this example.

Clarification: ask only for information necessary to continue safely, such as unresolved footprint, entrance, target level or design intent. Reuse validated supplied inputs instead of asking again. Show labelled fields, units and concise reasons; identify recommended options without pre-submitting them. Retain custom input, required/optional semantics, versioned question identity, draft preservation, field errors, pending state and a single atomic submission. Hosted questions and native OpenCode questions use different payloads; preserve native multi-select/custom rules rather than flattening them into the hosted schema. A question answer never grants native write approval.

Next prompts: at most three relevant, bounded text suggestions after a completed response. Examples depend on available evidence: compare the current alternatives, review recorded room areas, or request a layout adjustment. Do not suggest unsupported exports or imply measured BOQ data from a concept. Suggestions are drafts, not calls to accept_plan, approve, prepare_build or execute. Preserve exact proposal approval cards separately. Empty or ungrounded suggestions may simply be omitted.

## Harness findings and required contract

The deployed legacy workflow preserves full answer text and already accepts groups of1–4 clarification questions with units, options and an exact question/version reply. It has no separately bound summary or post-completion prompt suggestions. Its accepted finish_answer answer is bounded to3000 characters. The local OpenCode path preserves longer actual answers and distinct question arrays, native messages, tools and todos; it also has no authoritative summary/suggestion DTO. Existing pendingSteps and task-plan rows are not future user prompts.

Propose an optional versioned presentation record produced at finalization and saved with the actual answer. It must bind task, stable server-projected turn identity and answer revision/content identity. It carries a concise summary and up to three text prompts. Generate or omit it after deterministic outcome/answer rewrites; validate structural bounds and keep factual/native status governed by recorded outcomes. Unknown, foreign or mismatched presentation data is ignored. This requires persistence, allowlist and task projection work in each actual runtime, not just a new frontend prop.

Implemented contract: an optional answer-row presentation uses schemaVersion1, public taskId, stable execution turnId, SHA-256 answerHash, summary up to600 characters and at most3 text prompts up to180 characters each. The row also exposes turnId independently. The summary must be a contiguous passage of the exact saved answer; hash/bounds/identity checks and obvious approval/execution-prompt rejection run on server and client. These checks establish binding, not complete semantic proof that every caveat was selected. Only completed unchanged finish_answer results are eligible; deterministic rewrites and local OpenCode free-text results omit the DTO. The source change is not deployed.

Legacy fallback remains explicit: retain the actual answer; if shown compactly, label it as a preview with Full answer access, not as a new factual summary. Inline Markdown labels are normalized for readability while exact full text remains unchanged. Never summarize a failed task as successful or treat context estimates as native measurements. Raw conversation indices/IDs/CSV provenance remain exact; a separate answerNumber supplies human-facing labels.
