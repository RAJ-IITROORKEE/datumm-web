## Prioritized findings and proposed next work

1. **P1 — The entry path does not yet fulfill import → inspect → ask → save/revise.** The only web attachment action is disabled, and Assets explicitly says upload/preview requires Desktop. A user with an RVT therefore has no evidenced web import/render journey. This is a missing capability/contract, not a cosmetic defect. Design a truthful entry and empty state now around existing generated plans and available saved references; separately specify accepted formats, authorization, upload/storage, conversion/render pipeline, failures, provenance and retention before offering import. Do not imply an RVT can be parsed in the browser or that Desktop supports a particular format without qualification.

2. **P1 — 2D is a bounded sheet interaction, not the requested navigable plane.** The frame is a white scroll area with a fixed 20px CSS dot pattern; zoom scales the layer and Ctrl+wheel changes zoom without a cursor anchor (`plan-canvas.module.css:3-4,54-62`; `plan-canvas.tsx:231-237`). Drag is conditional on left button, tool and zoom, and there is no explicit touch-action in this component's frame rule. The available shortcut is stated in an accessible label but not visibly taught near the drawing. This supports the user's “white sheet” observation as a source-backed design gap, not a rendered verdict. Propose a tested pan/zoom interaction model, visible initial guidance, fit/reset and consistent touch/keyboard alternatives; validate synthesized gestures and physical devices before promising them. A world grid would need coordinates, scale and behavior specified; the present dots are decorative screen-space texture.

3. **P1 — Saved view expectation is unsupported.** In-memory 2D state and the mounted 3D view survive section/focus switches for the same identity; reload, replacement and explicit named camera views are not persisted (`plan-canvas.tsx:45-53,72-76,229`; `workspace.tsx:973-976`). Local comments survive separately. Make “view retained while open” and “comments saved on this browser” distinct. Named/reloadable views require an agreed storage owner, account/project scope, camera schema, identity and conflict handling; do not label a camera preset as saved.

4. **P2 — 3D is complementary schematic geometry, with narrow selection semantics.** Geometry derives from walls/openings/room rectangles rather than arbitrary model meshes; ray picking only finds rooms (`plan-three.tsx:31-46,88-99`). Unlike 2D, wall/opening selection and measurement are unavailable. Disablement of 3D has a title but requires discovering why (`plan-canvas.tsx:60,203`). Explain “generated cutaway” and its missing geometry near the tab; show an actionable unavailable state, preserve exact 2D fallback, and design consistent selection/measurement only for data the graph can support. Native model viewing is a separate integration.

5. **P2 — A light technical surface is intentional, but preview and print need separate design decisions.** 2D uses white paper/black ink and the 3D renderer explicitly clears to white (`plan-canvas.module.css:3-4,54`; `plan-three.tsx:123-128`). App chrome follows theme while sheet/export remains light (`plan-drawing.tsx:7-9`). Explore a more spatial viewer background/grid and contrast in both themes while preserving a legible light technical export; do not present a theme preference as changing geometry or native Revit.

6. **P2 — Export and revision provenance are split across places.** Display offers local view PNG/PDF while Exports offers server exact saved drawing links, supported by task/plan/version/style (`plan-canvas.tsx:169-175,211`; `plan-details.tsx:32-40`). Comparison chooses the immediate predecessor or another candidate (`use-workspace-state.ts:843-855`) and does not provide a full timeline. Make the two export types and their source/version/style explicit at the action, and clarify that comparison is limited to available saved versions. A full revision browser requires an authoritative listing contract; D9 report history remains deferred in `work-area-contracts.md:130,154`.

7. **P2 — Measurement and comments need better discovery and limitations.** Measure is an icon-only 2D tool with status instructions after selection and snaps to wall endpoints; comments must land inside rooms (`plan-canvas.tsx:177-192,254-269,287`). Give a visible tool label or concise onboarding and disclose units, snapping, local-only persistence and draft-only assistant handoff in context. Do not suggest model-grade measurement, synchronized review or automatic submission.

8. **P2 — Touch and keyboard parity need actual interaction evidence.** 2D has keyboard pan/zoom, room selection has a select control, and 3D has camera preset/zoom buttons. 3D advertises drag orbit but its canvas is an image role (`plan-three.tsx:112,145-158`), so arbitrary orbit has no evident keyboard equivalent in this source. Coarse-pointer 3D buttons are 36px, with triad buttons excluded from that override (`plan-three.module.css:9,16,20,30`); cascade and rendered target spacing need verification before a conformance finding. Test 320/390px, browser zoom, pointer cancel, touch pan/pinch, keyboard camera alternatives and focus restoration. UI Pro Max's local touch search recommends adequate spacing and context-appropriate targets; it is guidance, not proof of a failure.

## Preserve and qualify

The existing exact identity guard, explicit local-comment recovery, read-only comparisons, task-scoped outputs, 2D fallback on WebGL failure and explicit native approval boundary are useful foundations. The approved work-area contract keeps the viewer mounted across tab/focus changes; retain that continuity. Follow-on design should specify empty/loading/error/unsupported and disconnected states, and test real generated plans, narrow layouts and both themes. No claim here establishes deployed upload, RVT compatibility, native execution, full Revit feature parity, service version history or a completed visual audit. Scores and a detector verdict are intentionally omitted because rendered, performance and accessibility checks were outside this read-only source pass.

## Live observation and confirmed direction — supplementary

The parent inspected an actual saved task on 13 November. In 2D the viewport frame was `rgb(255, 255, 255)`; zoom reached 125% (drawing width 533px / scroll width 666px), ArrowRight moved `scrollLeft` by 80px, and Fit returned to 100%. In 3D the cutaway loaded on a white background, with ISO/TOP/FRONT controls and Bath selected. Room labels appeared as nearly white chips against the white view in `artifacts/ux/product-audit-3d.jpg`. This is an observed separation/discoverability concern; no contrast ratio was measured, and the observation does not establish a WCAG failure.

Source explains the likely low boundary separation: the renderer clear color is `#ffffff`, and each room sprite is painted with a 90%-opaque white rectangle; its text is intended to be dark `#202124` (`src/components/plan-three.tsx:81-86,120-127,140-142`). Sprites use transparent material with depth testing disabled, so they overlay the view (`plan-three.tsx:85`). White against white gives little chip boundary even when the dark text is legible. Inspect the rendered label text and chip in the final viewport and both themes before choosing a treatment; preserve readable labels and do not claim a measured contrast result from source colors alone.

The user has now confirmed a **dark drafting canvas** with a **white sheet/print** treatment, and the primary workflow is **generate → review → revise**. Project Brief and Decisions memory are the first memory priorities. This supersedes the earlier recommendation to merely explore viewer background direction; it is a direction for a later agreed design and implementation, not authorization to alter the app in this audit. Keep screen canvas, technical sheet export, exact identity, and memory persistence contracts explicit when planning.
